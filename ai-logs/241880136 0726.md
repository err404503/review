# 后续论文分析 1：Aleph Filter

> 论文：Aleph Filter: To Infinity in Constant Time
> 作者：Niv Dayan, Ioana-Oriana Bercea, Rasmus Pagh
> 发表：PVLDB 2024 (Vol.17, No.11, pp.3644-3656)
> 引用数：13（Semantic Scholar）

---

## 1. 研究对象

扩展型近似集合成员过滤器（expandable approximate set-membership filter）。支持插入、查询、删除，数据量可无限增长，过滤器可随之扩展。

## 2. 此前未解决的问题

已有扩展型过滤器（如 Quotient Filter 的 Fingerprint Sacrifice 方法、InfiniFilter）在扩展时面临至少一个痛点：查询/删除性能下降、内存占用过大、假阳性率飙升、或**无法无限扩展**（expansion 次数有限制）。没有方案同时做到"恒定时间操作 + 无限可扩展 + 内存与假阳性率可控"。

## 3. 主要结论（非技术语言）

Aleph Filter 是一个可以无限扩展的过滤器，**无论数据增长多少，插入、查询、删除都是常数时间**。如果提前知道数据会增长到多大，它的内存占用和假阳性率可以做到和静态过滤器（容量固定的最优过滤器）一样好。

## 4. 为什么困难

扩展现有过滤器时，哈希表容量翻倍，原本的指纹（fingerprint）需要被重新映射到更大的地址空间。常见做法是牺牲指纹的一个 bit 来扩展地址（Fingerprint Sacrifice），但这导致指纹越来越短，假阳性率翻倍翻倍再翻倍——不可持续。"无限扩展"意味着指纹不能无限变短，需要在某个地方做额外处理。

## 5. 核心方法总体思想

Aleph Filter 构建在 Quotient Filter 和 InfiniFilter 之上。核心方法是：

- **Fingerprint Sacrifice**：每次扩展牺牲一个指纹 bit 来获取额外地址位
- **Void Entries 复制**：将"空条目"在扩展后的哈希表中复制到两个可能的槽位上，使查询能从任一路径找到，只需一次查表
- **Tombstones 删除**：被删条目转为墓碑标记，扩展时利用原始哈希值定位并清除所有重复副本
- **Widening/Predictive 两种工作模式**：
  - Widening 模式：从短指纹开始，逐步加长（与本文原论文 §3 的下界匹配）
  - Predictive 模式：有数据规模预估时，提前分配较长指纹，保证最终状态与静态过滤器同等优秀

## 6. 与本论文的联系：A. 直接研究同一个问题

**论文明确引用并讨论了我们的论文**（§7 Related Work）：

> "Pagh, Segev, and Wieder prove a lower bound that if we initialize a filter to constant capacity and expand it to contain N keys, the filter must at some point use at least lg lg N bits per key in addition to what is required for a filter with a fixed capacity of N keys [43]. Aleph Filter's Widening and Predictive Regimes both meet this lower bound."

Aleph Filter 声称其 Widening 和 Predictive 两种模式**都达到了本文定理 1.1 的下界**。Rasmus Pagh 同时是两篇论文的合著作者——Aleph Filter 可以看作 Pagh 本人对 2013 年理论成果的工程实现。

## 7. 类比失效之处

- 论文是**理论证明**（下界 + 上界构造），Aleph Filter 是**实际工程系统**（基于 Quotient Filter 的哈希表实现）。它不提供新的下界证明，只提供满足下界的工程构造。
- 论文的两构造使用 Raman-Rao 紧凑字典做底层的精确存储。Aleph Filter 使用完全不同的一族技术：Quotient Filter + Robin Hood hashing + Fingerprint Sacrifice。
- 论文的下界对任意近似成员结构成立。Aleph Filter 是其中一个合规的实现，但不是一个"更好的下界"。
- 论文模型假设可以对元素序列分段重新初始化（Mode 2 过渡）。Aleph Filter 不需要提前分段——它用在线方式在每次扩展时处理。

## 8. 建议阅读顺序

1. **Abstract**（第 1 页）— 了解三个贡献
2. **§1 Introduction** 前 3 段（第 1–2 页）— 了解"为什么需要动态过滤器"
3. **§7 Related Work**（第 12 页）— 重点读引用 [43]（即本文论文）的那一段
4. **§2 Background**（第 2–4 页）— 了解 Quotient Filter 和 InfiniFilter 技术背景
5. **结论**（末尾页）— 总结

# 后续论文分析 2：Resizable Retrieval

> 论文：Resizable Retrieval
> 作者：William Kuszmaul, Aaron Putterman, Tingqiang Xu, Hangrui Zhou, Renfei Zhou
> 发表：2026 (arXiv:2606.15944)
> 引用数：0（预印本）

---

## 1. 研究对象

**可伸缩的动态检索数据结构**（resizable dynamic retrieval）。检索数据结构编码函数 $f: K\to[2^v]$（键→值），查询时对 $x\in K$ 返回 $f(x)$，对 $x\notin K$ 允许返回任意值。需要支持插入和删除，并且空间随**当前集合大小 $n$**（而非预设上界 $N$）参数化。

## 2. 此前未解决的问题

Demaine et al. 2006 [DMPP06] 解决了一个相近的问题：给定上界 $N$，可以做到 $Nv+O(N\log\log(U/N))$ 位空间 + O(1) 时间。但他们留了一个**开放问题**：能否把空间 bound 中的 $N$（预设上界）替换为当前实际大小 $n$？即"可伸缩性"（resizability）——数据结构的空间能随 $n$ 变化而自适应收缩和扩张。长达近二十年无人解答。

## 3. 主要结论（非技术语言）

可以做到。存在一个"可伸缩"的动态检索结构，空间在最坏情况下与当前集合大小 $n$ 成正比，且操作时间为 $O(1)$。论文还证明了**匹配的下界**——说明这个空间-时间 tradeoff 是最优的。作为推论，论文进一步给出了动态过滤器的一个新构造。

## 4. 为什么困难

当过滤器收缩时（删除元素），已分配给旧元素的短指纹无法简单地"变长"——它们的信息在压缩过程中丢失了。这会导致不存在的碰撞（不同键的短指纹发生碰撞，但无法区分）。

另一个困难：早期插入的元素拥有较短的指纹，当集合变大时，短指纹之间的碰撞概率上升，需要一种方法"分摊"碰撞风险。

论文用一个额外结构（"midyard"）处理收缩时的碰撞问题——为需要更多辨识信息的键存储超长指纹。

## 5. 核心方法总体思想

1. **延长"碰撞风险"分摊技术**——这个技术最初用于 [PSW13]（即我们的论文！）和 [BE22] 的插入场景。论文将其推广到支持删除的完整动态场景。

2. **引入 midyard**：一个辅助结构，为那些"在收缩时可能与其他键碰撞"的键存储额外长指纹。midyard 的容量被严格控制→总体空间不会炸。

3. **去摊销化**：使每次操作的时间在最坏情况下都保持 $O(1)$，而不是期望或摊还。

4. **推论**：该检索结构可以直接用作动态近似成员过滤器——存 0 位值时成为过滤器。

## 6. 与本论文的联系：A+B 混合

- **A. 直接研究同一个问题**（部分）：论文明确引用 [PSW13]（我们的论文！）中使用的"碰撞风险分摊"技术，并称其是本文方法的前身之一。论文所解决的"resizability"问题，正是我们论文中 §1 所指出的核心困难——"the size n of the set is not known in advance"。

- **B. 使用相近的数学方法**：两种论文都使用了分层/分阶段构造 + 碰撞概率控制。本文的 midyard 与构造 2 的桶化有结构上的相似性（辅助结构处理边缘情况）。

## 7. 类比失效之处

- 论文解决的是**检索**（retrieval）问题，不是近似成员（AM）。检索允许 $x\notin K$ 时返回任意值，比 AM 约束更弱。检索可以用来构建 AM（作为推论），但不是同一问题。
- 论文的空间 bound 参数化为**当前 $n$** 而非预设 $N$，但这是"dynamic resize"概念——我们的论文参数化的是"未知最终 $n$"（但结构可以是 growing 的，不必 shrinking）。
- 论文没有提供像我们论文那样的精确下界（$\Omega(n\log\log n)$ 附加项）——它的下界是关于整体空间-时间 tradeoff 的，而非专门针对未知 $n$ 场景。

## 8. 建议阅读顺序

1. **Abstract**（第 1 页）— 了解问题、结论
2. **§1 Introduction 的"this paper"段落**（第 2–3 页）— 了解技术路线概要（含碰撞风险、midyard、去摊销）
3. **推论部分**（介绍中提到的 "corollaries for dynamic filters"）— 了解与近似成员的具体关联

# 后续论文分析 3：Dynamic "Succincter"

> 论文：Dynamic "Succincter"
> 作者：Tianxiao Li, Jingxun Liang, Huacheng Yu, Renfei Zhou
> 发表：FOCS 2023 (arXiv:2309.12950)
> 引用数：9（Semantic Scholar）

---

## 1. 研究对象

动态扩充的 B-tree（augmented B-tree, aB-tree）的紧凑表示。目标是将 Pǎtraşcu 2008 的静态 "Succincter" 成果动态化——让 aB-tree 在支持更新的同时保持极低冗余（仅 3 bit）。

## 2. 此前未解决的问题

Pǎtraşcu 2008 证明：任何 aB-tree 在**静态**场景下只需 2 bit 冗余即可存储。但如何**动态化**它——支持插入和删除同时保持亚线性冗余——此前没有人做到。已有的动态紧凑数据结构（如 Raman-Rao [RR03]）冗余为 $o(n)$ 位，但无法压到 ≤ 3 bit 的绝对上界。

## 3. 主要结论（非技术语言）

将 aB-tree 动态化成功了。得到的**动态 aB-tree (daB-tree)** 仅需 3 bit 冗余（通过查表辅助），支持更新和查询，时间为深度的多项式函数。作为应用，构造了一个动态 rank/select 数据结构，其更新和查询时间达到已知下界的最优（$O(\log n/\log\log n)$），冗余为 $o(n/\log n)$——此前没有动态 FID 能同时达到这样的时间和空间。

## 4. 为什么困难

静态 Succincter 使用**全局编码**——将整棵树的布局信息压缩到极少数 bit 中。动态化意味着每次插入/删除都可能改变树的全局布局——需要重新压缩。如何在不重建全树的前提下保持 3 bit 冗余是核心技术挑战。

## 5. 核心方法总体思想

不直接动态化 Succincter 的全局编码。而是在 daB-tree 的每个节点内部使用**小型静态 Succincter** 做局部编码，树的整体结构通过标准 B-tree 方法维护。这样更新只影响局部节点，而 3 bit 冗余是在全局摊销后达到的。

## 6. 与本论文的联系：C. 概念类比

- 论文在参考文献中引用了 [PSW13]，将其列入"succinct dictionaries and filters"（紧凑字典和过滤器）类别，作为紧凑数据结构的**应用**之一。但 Dynamic Succincter 没有引用论文的结果或方法——仅作为背景文献列入。
- 联系是间接的：论文使用 RR03 紧凑字典作为构造 2 的底层引擎。Dynamic Succincter 提供了比 RR03 更紧凑的动态字典（冗余从 $o(n)$ 降至 $O(n/2^{\log^{0.199}n})$）——但论文的未知 $n$ 框架与底层字典的冗余优化是两个正交维度。论文的 $O(n\log\log n)$ 额外开销来自"未知 $n$"框架，而非字典冗余。

## 7. 类比失效之处

- 论文问题的难度在于**"不知道 $n$"的框架层面**（何时创建新字典、如何过渡、如何控制假阳性不爆）。Dynamic Succincter 解决的是**底层字典的空间紧凑性**（冗余多小能接受）。两者可叠加但不能相互替代。
- 论文的两构造都假设底层字典已经是紧凑的（RR03 的 $B+o(B)$ 被当作黑盒使用）。替换底层字典为 Dynamic Succincter 只会改进低阶项，不会改变论文的核心贡献（$\Omega(n\log\log n)$ 下界和 $O(n\log\log n)$ 上界框架）。
- Dynamic Succincter 不区分已知 $n$ 和未知 $n$——它只提供一个字典，容量由外界指定。论文的框架负责"何时创建新字典、何时过渡"——这是 Dynamic Succincter 不涉及的层次。

## 8. 建议阅读顺序

1. **Abstract**（第 1 页）— 了解核心结论
2. **§1 Introduction**（第 2–3 页）— 了解紧凑数据结构的历史和动态化的挑战
3. **§1 Introduction 末尾**— 了解 daB-tree 的 high-level 思路（局部静态 Succincter + 全局动态维护）
